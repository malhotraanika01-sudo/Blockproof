SYSTEM ARCHITECTURE — V1.0

BlockProof

Blockchain-based digital crime reporting, evidence integrity & investigation management system. Three isolated frontends, a single RBAC-protected Express API, PostgreSQL for relational state, and Hyperledger Fabric for immutable custody/integrity records.

1. Layered overview

Client layer — 3 separate React apps/bundles
Common User Portal
Public reporting site. Report crime, upload evidence, track status.
Investigator Workspace
Assigned cases, evidence review, transfers, verification.
Head Command Center
Full access, analytics, audit logs, blockchain history.
React + Tailwind CSS + Framer Motion + Lucide React + Recharts + React Router · each talks to the same API over HTTPS/REST with a JWT
Application / API layer
Express.js REST API (Node.js)
• JWT auth middleware
• RBAC middleware (role/permission checks on every route)
• Multer — file upload handling
• Route controllers: Reports, Cases, Evidence, Transfers, Verification, Users, Analytics, Audit, Blockchain
• Validation & centralized error handling
• Prisma Client — DB access
Single API, RBAC enforced server-side — never trust hidden UI. Common User and Investigator get 403 on blockchain-history routes; only Head passes.
Security / cryptography layer (invoked by API layer)
JWT
Session/auth tokens, role claims
Argon2 / bcrypt
Password hashing
AES-256-GCM
Encrypts evidence bytes (confidentiality)
SHA-256
Evidence fingerprint (integrity)
Data & ledger layer
PostgreSQL (via Prisma ORM)
~14 normalized tables: Users, Roles, Permissions, Crime_Reports, Cases, Evidence, Evidence_Types, Evidence_Transfers, Investigation_Updates, Forensic_Analysis, Court_Submissions, Evidence_Locations, Blockchain_Transactions, Audit_Logs
Encrypted file storage
AES-256-GCM ciphertext blobs. Files referenced from Evidence table by pointer/key, never stored on-chain.
Hyperledger Fabric
Permissioned ledger. JS chaincode: CreateEvidence, TransferEvidence, VerifyEvidence, GetEvidence, GetEvidenceHistory. Stores hash + custody events only.

2. Request path & RBAC gate

Client (Common User / Investigator / Head) │ HTTPS + Bearer JWT ▼ Express API — verifyJWT() → attach {userId, roleId} │ ▼ RBAC middleware — checkPermission(route, role) │ ├─ Common User → Reports/Evidence-upload routes only (403 elsewhere) ├─ Investigator → Assigned-case, evidence, transfer, verify (403 on /blockchain/*, /users/*) └─ Head → All routes, incl. /blockchain/*, /audit/*, /users/* │ ▼ Controller → Service → Prisma → PostgreSQL └→ (evidence ops) Crypto service → Fabric Gateway → Chaincode

3. Evidence upload & integrity flow

Upload / custody event
  1. Common User uploads file via portal (Multer)
  2. Backend validates file type/size
  3. SHA-256 hash computed over original bytes
  4. AES-256-GCM encrypts the file
  5. Encrypted blob → file storage; metadata row → PostgreSQL (Evidence table)
  6. Hash + evidence ID + event type + timestamp → Fabric chaincode CreateEvidence()
  7. Returned Fabric tx ID stored in Blockchain_Transactions
Verification event
  1. Investigator/Head clicks Verify on an evidence item
  2. Backend decrypts (as authorized) and recomputes SHA-256
  3. Compares against hash on record / chaincode VerifyEvidence()
  4. Match → VERIFIED · Mismatch → TAMPERING DETECTED
  5. Result written to Audit_Logs (trigger-backed)
  6. Investigator sees pass/fail only — not the raw ledger
  7. Head can additionally open full custody history GetEvidenceHistory()
